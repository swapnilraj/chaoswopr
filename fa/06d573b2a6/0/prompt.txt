# Phase 1 Implementation Plan: Parallel Coordination with Test-First Development

## Context

Phase 1 of chaoswopr establishes the foundation infrastructure (testnet deployment, monitoring, safety systems, scenario schema) that all subsequent phases depend on. The phase has 23 tasks across 4 parallel tracks (A-D) with a 4-6 week timeline.

**Challenge**: Multiple subagents need to work on different tracks simultaneously without conflicts, using deterministic success criteria and test-first development to ensure quality gates before any production code is written.

**Why This Matters**:
- Phase 1 blocks Phase 2 and 3, so efficient parallel execution is critical to project timeline
- Safety systems must be tested extensively before chaos injection begins in Phase 2
- Infrastructure bugs are expensive to fix later - catching them early via tests saves weeks
- Deterministic tests enable autonomous agent coordination without human verification bottlenecks

## Recommended Approach

### 1. Parallel Subagent Coordination Architecture

**PostgreSQL-Backed Task Registry**
- Central `tasks_registry` table tracks all 23 tasks with status (pending, claimed, in_progress, completed, failed)
- Agents use atomic row-level locking (`FOR UPDATE SKIP LOCKED`) to claim tasks without conflicts
- Task dependencies explicitly encoded (e.g., B1 blocks on A2 completion)
- Automatic task prioritization: Track D (shortest, no deps) → Track C (independent) → Track A (blocks B) → Track B (needs A2)

**Agent Heartbeat and Liveness**
- Agents update heartbeat every 30 seconds while working
- If heartbeat stale > 5 minutes, task auto-reclaimed by another agent
- Enables resilient handoff if agent crashes

**Conflict Prevention**
- Each track has isolated directories: `infrastructure/testnet/`, `infrastructure/monitoring/`, `safety/`, `scenarios/`
- Shared files use explicit locking or append-only protocols
- Git commits per task create rollback points

**Progress Communication**
- Redis Pub/Sub for real-time events: `task.claimed`, `task.completed`, `task.failed`
- Agents subscribe to dependency completion events to know when their tasks unlock

### 2. Deterministic Success Criteria

Every task has precise, measurable, programmatically verifiable success conditions. Examples:

- **A2 (50-node testnet)**: Finality within 3 epochs (38.4s), 95% success rate over 20 test runs
- **B2 (metrics catalog)**: All 50+ metrics from `metrics_catalog.yaml` present in Prometheus, query each metric and assert > 0 datapoints
- **C2 (circuit breaker)**: Service transitions `armed` → `tripped` within 10s of alert firing, API returns correct state
- **D3 (baseline scenario)**: Runs end-to-end without error, writes metrics to PostgreSQL (assert > 0 rows), writes audit log to S3

All 23 tasks mapped to automated tests - see deterministic success criteria table in plan.

### 3. Test-First Implementation Strategy

**Core Principle**: Write tests BEFORE production code for every task.

**Test Structure**:
```
tests/
├── unit/           # Fast (<1s), mocked dependencies
├── integration/    # Real services in Docker (5-30s)
├── e2e/           # Full Kurtosis enclaves (1-10 min)
├── fixtures/      # Mocks and sample configs
└── conftest.py    # Pytest fixtures
```

**Test Framework**: pytest + testcontainers-python + Kurtosis SDK

**Implementation Order** (4 weeks):
1. **Week 1**: Foundational testing infra + Track D tests (schema, validator, baseline scenario mock)
2. **Week 2**: Track C tests (safety system) + Track A tests (testnet infrastructure)
3. **Week 3**: Track A E2E tests (50-node finality, mainnet fork) + Track B tests (monitoring)
4. **Week 4**: Track B completion + cross-track integration tests (isolation, snapshots)

**Why This Order**:
- Track D first: Shortest (1 week), no dependencies, defines contracts for other tracks
- Track C second: Independent, critical for safety, can run parallel with Track A
- Track A third: Longest, blocks Track B, but most critical for E2E
- Track B last: Depends on A2, can start once testnet bootstraps

### 4. CI/CD Pipeline Design

**GitHub Actions Workflow** (`.github/workflows/phase1-ci.yml`):
- **unit-tests** job: < 5 min, runs on every push
- **integration-tests** job: < 15 min, real PostgreSQL + MinIO services
- **e2e-tests** job: < 30 min, real Kurtosis enclaves (excludes 200-node scale test)
- **exit-criteria-validation** job: Runs `validate_exit_criteria.py` for all 7 criteria

**Total CI Time Target**: < 10 minutes (parallel jobs)

**Exit Criteria Automation**:
- Script: `scripts/validate_exit_criteria.py --criteria <1-7>`
- EC1: Testnet boots reliably (95%+ success over 20 runs)

**Quality Gates**:

- Exit criteria validation 95%+ success rate

### 5. Subagent Assignment Strategy

**3 Subagents Working in Parallel**:

**Agent 1 (Infrastructure Specialist)**
- Week 1: Set up testing infrastructure, Track D tests (D1-D4)
- Week 2-3: Track A tests (A1-A7), Track B tests (B1-B6)
- Week 4: Track B completion, integration tests

**Agent 2 (Platform Specialist)**
- Week 1: Set up fixtures and mocks, Track D implementation (D1-D4 code)
- Week 2: Track C tests (C1-C6), Track C implementation
- Week 3-4: Track D baseline scenario E2E, Track C snapshots/isolation (needs Track A)

**Agent 3 (Generalist)**
- Week 1: CI/CD pipeline, contract tests for external dependencies
- Week 2: Track A implementation (A1-A7) parallel with Agent 1's tests
- Week 3: Track B implementation (B1-B6) once A2 completes
- Week 4: Exit criteria validation script, final integration

**Coordination Protocol**:
1. All agents start by claiming tasks from PostgreSQL registry (highest priority available)
2. Agents announce task claims via Redis (`task.claimed` event)
3. When agent completes task, run its acceptance tests
4. If tests pass: mark `completed`, publish `task.completed` event, commit code
5. If tests fail: mark `failed`, retry up to 3 times, escalate to human if still failing
6. Agents continuously poll for newly-unlocked tasks (dependencies satisfied)
